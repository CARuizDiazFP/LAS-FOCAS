# PR Diario - 2026-09-11

## Resumen

Se cierra la rama `feat/cromo-camino-optico` con la implementación del recorrido óptico de Cromo vía `/network/fo/{id}/path`, validado con pruebas unitarias y de wiring sobre los endpoints web.

La feature resuelve tres capas:

1. cliente HTTP de Cromo con manejo de timeout y limitador propio para `/path`;
2. parseo y auditoría del grafo del camino, con semilla, lados, ODFs y consistencia local;
3. serialización y endpoints para que la UI y el admin puedan consumir el resultado sin tocar la red desde el frontend.

## Qué quedó hecho

- `core/services/cromo/client.py`: `get_camino_optico` con `projview`, lista de pelos, timeout propio y manejo de errores de Cromo.
- `core/services/cromo/camino_optico_service.py`: normalización del payload, resolución de la raíz, lados, estadísticas, ODFs, consistencia y caso `SIN_SEMILLA`.
- `core/services/cromo/camino_optico_txt.py`: render del tracking legacy con formato compatible con el parser histórico.
- `web/app/main.py`: 3 endpoints nuevos para semilla, tracking `.txt` y camino completo con auditoría.
- `web/frontend/...`: API client, composable y UI para revisar el camino, la secuencia y la asociación de ODF.
- `tests/...`: suite específica del feature (`118 passed` en la batería focalizada).

## Riesgos y límites conocidos

- `lasfocasdev-web` fue reconstruido y su health HTTP respondió 200; falta completar la verificación autenticada de los endpoints de camino óptico en el stack dev.
- `SIN_SEMILLA` está modelado como respuesta válida (HTTP 200 en el admin) para evitar falsos incidentes en el 77% del universo sin pelo.
- La auditoría de consistencia sigue siendo diagnóstica y no bloquea el flujo; el objetivo es mostrar discrepancias y no ocultarlas.
