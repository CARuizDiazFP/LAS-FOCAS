# PR Diario - 2026-08-07

## Resumen de Cambios

Etapa 7 del módulo de ingesta Cromo: la ejecución de la ingesta se movió de un `asyncio.create_task`
dentro del proceso `web/app/main.py` (Etapa 4) a un **worker Docker dedicado** (`cromo_worker`), pedido
explícito del usuario para poder programar corridas periódicas sin competir con el tráfico del panel.
El worker expone control HTTP (FastAPI + `AsyncIOScheduler`, sin threads) con `/health`, `/reload` y
`/run`; el intervalo/hora de inicio/parámetros del ciclo periódico se configuran desde una tabla nueva
(`app.cromo_ingesta_config`, fila única) editable desde una card nueva en el panel — arranca
**deshabilitado por defecto**.

De paso, dos correcciones reales encontradas por el usuario al usar la vista contra los datos ya
ingeridos en producción de dev (corridas reales completas, corrida `id=8`: 80.619 leídas, 32.782
cables, 11.100 botellas, 1.275.234 pelos): un bug de frontend (`k.value.trim is not a function` al
poner un valor en "Máximo de páginas") y un pedido estético (cabecera de "Ingesta de Cromo" mal
alineada respecto al patrón ya usado en `/servicios`) que se resolvió normalizando las 6 vistas admin
existentes a un componente de cabecera común.

## Cambios Realizados

### Worker dedicado — `modules/cromo_worker/`

- `worker.py`: `app = FastAPI()` con `GET /health`, `POST /reload`, `POST /run`
  (`{"corrida_id": int|null, "usuario": str|null}` — con `corrida_id` continúa una corrida ya creada
  leyendo sus propios `params` persistidos; sin él, crea una corrida nueva desde
  `cromo_ingesta_config`). `AsyncIOScheduler` + `IntervalTrigger` (mismo `_build_trigger` que
  `slack_baneo_notifier`, anclado a `hora_inicio` GMT-3 si se indica). `_reconciliar_corridas_huerfanas()`
  al arrancar: cierra como `FALLIDA` cualquier fila `EN_CURSO` de un proceso anterior. Todo en el
  mismo loop de asyncio — sin threads, sin `run_coroutine_threadsafe` (a diferencia del precedente de
  Slack, que es 100% síncrono y por eso usa `http.server` + threads; el dominio Cromo ya es 100%
  async, así que FastAPI + `uvicorn.Server(...).serve()` como una coroutine más es más simple y sin
  riesgo nuevo de concurrencia).
- `config.py`: constantes (`NOMBRE_SERVICIO`, `USUARIO_SCHEDULER`, `HEALTH_PORT=8096`, `JOB_ID`).
- `requirements.txt`: sólo `apscheduler>=3.10,<4` (no está en `common-requirements.txt`, igual que en
  el worker de Slack — cada worker declara sus deps extra en su propio archivo).
- `deploy/docker/cromo_worker.Dockerfile`: calco exacto del patrón de `slack_baneo_worker.Dockerfile`
  (`FROM focas-base:latest`, copia sólo `core/`, `db/`, `modules/__init__.py` + el módulo propio,
  usuario no-root `useradd -m -u 1000 worker`).
- `deploy/docker-compose.dev.yml`: bloque `cromo_worker` (secrets `db_password_v1` + `cromo_password_v1`
  ya declarado, `expose: ["8096"]`, healthcheck). `scripts/start_dev.sh`: agregado al array `SERVICES`
  — sin esto el flujo normal de arranque no lo hubiera levantado.

### Config del scheduler — `db/models/cromo.py` + migración

- `CromoIngestaConfig` (tabla `app.cromo_ingesta_config`, fila única): `habilitado` (default `false`),
  `intervalo_horas` (default `24`), `hora_inicio` (nullable), `psize`, `max_paginas` (nullable = sin
  límite), `clases` (JSONB), `ultima_ejecucion`, `ultimo_error`. Migración `20260806_01` (siembra la
  fila con los defaults de producto ya decididos: `psize=5`, las 5 clases de botella).
- No se reusó `app.config_servicios` (compartida con Slack): tiene columnas específicas de Slack
  (`slack_channels`) que no aplican, y de todas formas hacía falta una migración para las columnas que
  sí necesita Cromo (`psize`, `clases`, `max_paginas`) — se optó por una tabla propia, consistente con
  el resto del namespace `cromo_*`.

### `web/app/main.py`

- **Se elimina** `_correr_ingesta_cromo_en_background` (ya no se usa).
- **Se modifica** `POST /api/admin/ingesta/cromo`: sigue creando la corrida ahí mismo (para responder
  `corrida_id` de inmediato) pero delega la ejecución con `httpx.AsyncClient().post(.../run, json=
  {"corrida_id": ..., "usuario": ...})`. Si el worker no responde: `_marcar_corrida_fallida()` (nuevo
  helper) cierra la corrida como `FALLIDA` con el motivo, y el endpoint responde `503` — nunca queda
  `EN_CURSO` huérfana.
- **Nuevos**: `GET`/`POST /api/admin/ingesta/cromo/config` (leer/guardar la config del scheduler, el
  `POST` valida `psize`∈`PSIZE_PERMITIDOS`, `intervalo_horas`≥1, `hora_inicio` 0-23, `clases` no vacía,
  y le pide al worker `/reload` best-effort), `GET .../config/health` (proxy a `/health` del worker,
  mismo patrón que `servicios_baneos_health`), `POST .../config/trigger` (proxy a `/run` sin
  `corrida_id`, usando el username real del admin logueado para el audit trail).
- **Sin cambios**: `GET .../corridas/{id}/stream` (SSE), `GET .../corridas`, `GET .../corridas/{id}`,
  `POST .../corridas/{id}/cancelar` — los cuatro leen/escriben la DB directo, sin importar qué proceso
  ejecuta la ingesta.

### Frontend

- **Fix del bug real** `web/frontend/src/admin/views/AdminIngestaCromo.vue:326`:
  `maxPaginasInput.value.trim()` fallaba porque Vue 3 castea automáticamente a `Number` en cada evento
  `input` de un `<input type="number">` (aun sin el modificador `.number` en el `v-model`) — confirmado

- `web/frontend/src/api/cromo.ts`: `CromoSchedulerConfig`/`CromoWorkerHealth` (interfaces),
  `obtenerConfigSchedulerCromo`, `guardarConfigSchedulerCromo`, `obtenerSaludWorkerCromo`,

- `AdminIngestaCromo.vue`: card nueva "Scheduler automático" (toggle habilitado, intervalo, hora de
  inicio, clases/psize/max_páginas del ciclo — formulario independiente del de "Nueva corrida") +
  card "Estado del worker" (badge, última ejecución/error, "Verificar estado", "Ejecutar ahora") —
  mismo patrón que ya usa `AdminBaneos.vue` para el worker de Slack.
- `web/frontend/src/admin/components/AdminPageHeader.vue` (nuevo): cabecera kicker + heading-row +
  subtítulo, calcada 1:1 del patrón ya usado en `ServiciosView.vue` (la referencia visual que dio el
  usuario). Aplicada a las 6 vistas admin existentes: `AdminIngestaCromo`, `AdminIngestaCamaras`,
  `AdminIngesta` (hub), `AdminUsuarios`, `AdminServicios`, `AdminBaneos` — decisión tomada con el
  usuario (vía pregunta) de normalizar las 6 de una pasada en vez de sólo la que se había señalado.

## Impacto y Riesgos

- **Impacto operativo**: ninguno sobre producción de LAS-FOCAS — todo el cambio de arquitectura es
  dev-only. En dev, el comportamiento por default (`habilitado=false`) es idéntico a "no hay
  scheduler" — el único cambio de comportamiento observable es que la ingesta manual ahora depende de
  que `cromo_worker` esté corriendo (antes dependía sólo de `web`).
- **Riesgo nuevo, ya mitigado**: si `cromo_worker` se cae mientras el panel intenta disparar una
  corrida, el usuario ve un 503 claro en vez de un 202 engañoso — verificado explícitamente.
- **Riesgo conocido, aceptado**: activar el scheduler con `max_paginas=NULL` dispara corridas reales
  completas (del orden de horas, según la corrida real `id=8` de esta sesión: ~9.5 hs) de forma
  automática e inatendida. Mitigado por el default `habilitado=false` — activar el scheduler es una
  decisión explícita del admin, con la config de `psize`/`max_paginas`/clases visible en el mismo
  formulario donde se activa.
- **Sin auth entre `web` y `cromo_worker`**: la comunicación es interna a la red Docker
  (`lasfocas_dev_net`), no expuesta al host (`expose`, no `ports`) — mismo criterio que
  `slack_baneo_worker`. No hay nada que autentique el request de `web` al worker más allá del
  aislamiento de red; aceptable para este alcance (dev, red interna), a revisar si se lleva a prod.

## Compatibilidad y Migraciones

- **DB/Alembic**: migración nueva `20260806_01_cromo_ingesta_config.py`, aditiva (tabla nueva, sin
  tocar las existentes). `downgrade()` la elimina limpiamente.
- **Dependencias**: `apscheduler` nueva, pero acotada a `modules/cromo_worker/requirements.txt` (no
  afecta la imagen base ni otros servicios). `fastapi`/`uvicorn` ya estaban en `common-requirements.txt`.
- **Breaking changes**: ninguno para el contrato HTTP hacia el SPA (`POST /api/admin/ingesta/cromo`
  sigue devolviendo `corrida_id` de inmediato con el mismo shape). Internamente, `web` ahora depende
  de que `cromo_worker` esté disponible para que una corrida disparada desde el panel realmente
  corra — antes esa dependencia no existía (todo corría en el mismo proceso).
