### Transición de `focas-base` (ítem 1, ejecutada)
```bash
H=$(./scripts/build_base.sh --print-hash)    # 43c1cbcb39f3…
printf 'FROM focas-base:latest\n' | docker build -q --label "focas.requirements.hash=$H" \
  -t focas-base:latest -t "focas-base:req-${H:0:12}" -
./scripts/build_base.sh                      # "ya está actualizada (hash 43c1cbcb39f3...)", sin build
```
Es una imagen de sólo metadatos sobre las mismas capas: el disco no se movió (8268 MB libres antes y después).
`focas-base:latest` y `:req-43c1cbcb39f3` apuntan a `cbc3a1b5c4c2`; `:req-cde710aa4de8` (`88747ead8cb6`) queda
porque lo usan como base las imágenes de dev vigentes. Como `latest` cambió de ID, el próximo build de
cualquier servicio no aprovecha la caché desde el `FROM`. Habría pasado igual con un rebuild.

### Riesgos
- **Ventana del hash**: hasta que P24 llegue a `dev`, un `build_base.sh`/`start_dev.sh` con el script viejo compara
  el hash crudo (`8af3e71e776a`) con el label nuevo y **reconstruye la base**. No correrlos desde otro worktree
  hasta que esta rama integre.
- **`.env` de prod**: cambia la config de los 8 servicios que lo cargan (no `postgres`). El próximo `up` de
  cualquiera de ellos lo recrea, aunque no haya imagen nueva. En un deploy normal pasa igual.
- **Ítem 4 fuera del contenedor**: el venv y los tests ya no escriben en `web/data/` sino en `data/` (o en el env).
  En la imagen no cambia nada.
- **Botellas inventario**: no hay runner de tests de front. La paginación, los dos modos y el error se verificaron
  por build, tipos y CSS emitido. Falta la prueba logueada.
