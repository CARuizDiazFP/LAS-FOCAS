# PR Diario - 2026-09-03

## Resumen de Cambios

Dos acciones sobre producción a pedido del usuario, a partir de `docs/Doc Privada/Criticas en
seguimiento.xlsx`: (A) reconciliar el estado BANEADA/LIBRE de Cámaras/Botellas contra la lista de
críticas, ya aplicado y verificado; (B) preparar (sin desplegar todavía) el fix de baneos-hermanos
(`99a2306`, 2026-08-28) para los contenedores productivos — el usuario pidió posponer el
merge/build/restart a una ventana de mantenimiento. Detalle completo de decisiones en
`docs/decisiones.md`, entrada "2026-09-03 — Reconciliación de Botellas críticas en prod...".

### Parte A — Reconciliación aplicada en prod (sin cambios de código)

`docs/Doc Privada/Criticas en seguimiento.xlsx` lista Botellas (no Cámaras en sentido estricto), pero
sus 57 `nombre_botella` matchean 100% exacto contra `app.camaras.nombre` (legado) en prod — no hizo
falta ningún cambio de código ni migración, `aplicar_estado_a_grupo` ya corre en `lasfocas-web` tal
cual está desplegado hoy.

- Script de uso único (`docker cp` + `PYTHONPATH=/app` dentro de `lasfocas-web`), dry-run revisado
  con el usuario, luego `--apply` con commit real. Nunca `UPDATE` directo — todo vía
  `aplicar_estado_a_grupo` (auditoría completa en `CamaraEstadoAuditoria`).
- Resultado verificado contra `lasfocas-postgres` real: 3 Cámaras → `BANEADA`, 938 → `LIBRE` (44
  `BANEADA`→`LIBRE` reales, 894 `DETECTADA`→`LIBRE`), 565 `PENDIENTE_REVISION` sin tocar (pedido
  explícito del usuario, se eliminan después desde la UI), 794 sin cambio.
- Script borrado del contenedor al terminar.

## Impacto y Riesgos

- **941 filas reales de `app.camaras` mutadas en prod** (auditadas en `camaras_estado_auditoria`,
  usuario `reconciliacion_criticas_20260902`). Reversible fila por fila desde la auditoría si hiciera
  falta, pero no hay rollback automático de un solo comando.
- **De las 44 `BANEADA→LIBRE`**, varias (ids 2282-2322, un bloque consecutivo con nombres "Cámara
  <calle>") no siguen el patrón de nombre del resto del inventario — parecen registros
  padre/duplicados de un proceso legado. Ninguna tenía un `IncidenteBaneo` activo detrás, pero no hay
  forma de confirmar desde el sistema si alguien las banéo a mano por una razón real no trackeada
  como incidente. Señalado al usuario antes de aplicar; confirmó proceder.
- **`main` no refleja el código real desplegado en prod** — brecha de proceso descubierta, no
  corregida esta sesión (queda documentada para que el próximo diagnóstico de prod no asuma que
  `main` es la fuente de verdad).
- **La rama `fix-baneos-hermanos-prod` no se mergeó ni se desplegó** — a pedido del usuario, queda
  pendiente para la próxima ventana de mantenimiento. Sin ese paso, prod sigue expuesto al bug de
  baneos-hermanos (`docs/decisiones.md`, entrada 2026-08-28) para el próximo cierre casi simultáneo de
  incidentes hermanos.
