# PR Diario - 2026-06-25

## Resumen de Cambios

Se implementó hardening de seguridad en entorno dev para la API core, el panel web y el manejo de contraseñas. El objetivo fue cerrar accesos anónimos a rutas sensibles, evitar que el rate limit del login dependa de cookies, declarar flags de sesión explícitos y eliminar el truncado silencioso de contraseñas largas.

También se agregó una primera versión del histórico vivo de reportes web para SLA y Repetitividad, persistido en PostgreSQL y visible desde `/reports-history`.

## Contexto y Alcance

- **Módulos afectados**: `api`, `web`, `core/password.py`, `core/services/report_history.py`, migraciones Alembic, scripts dev, samples de entorno, tests y documentación.
- **Alcance operativo**: rama `dev` y stack de desarrollo; no se modificó `Legacy/`.
- **Decisión principal**: usar API key interna para la API core como mitigación mínima y compatible con servicios internos.

## Cambios Realizados

- `api/app/security.py`: nueva dependencia `require_api_key` con soporte para `Authorization: Bearer <key>` y `X-API-Key`.
- `api/app/main.py`: rutas `reports`, `ingest`, alias `/import` e `infra` quedan protegidas por API key.
- `api/app/routes/health.py`: `/db-check` queda protegido; `/health` y `/health/version` permanecen públicos.
- `web/app/main.py`: rate limit de login en memoria por IP + usuario, configurable con `WEB_LOGIN_RATE_LIMIT_MAX` y `WEB_LOGIN_RATE_LIMIT_WINDOW`.
- `web/app/main.py`: `SessionMiddleware` declara `SameSite=Lax`, `max_age` y `Secure` configurable con `WEB_SESSION_HTTPS_ONLY`.
- `core/password.py`: hashes nuevos con SHA-256 de la contraseña completa antes de bcrypt y prefijo versionado `$lasfocas-sha256-bcrypt$v1$`.
- `core/password.py`: compatibilidad con bcrypt legacy para contraseñas existentes y `needs_rehash` marcando legacy como migrable.
- `deploy/env.sample`, `deploy/env.dev.sample`, `deploy/docker-compose.dev.yml`: variables y secret dev para `LAS_FOCAS_API_KEY` / `api_key_v1`.
- `scripts/setup_local_secrets.sh` y `scripts/start_dev.sh`: generación idempotente de `api_key_v1.txt` para clones dev existentes.
- `scripts/check_no_plaintext_secrets.sh`: se corrigió falso positivo del propio script y se agregó control para `LAS_FOCAS_API_KEY`.
- Tests nuevos: `tests/test_api_auth.py`, `tests/test_password.py` y `tests/test_web_security.py`.
- Tests existentes de API core actualizados para enviar API key en escenarios válidos.
- Documentación actualizada en `docs/api.md`, `docs/web.md`, `docs/Seguridad.md`, `docs/infra.md` y `docs/decisiones.md`.
- `db/alembic/versions/20260625_01_report_history.py`: nueva tabla `app.report_history` para registrar reportes web con estado, usuario, fuente, período, duración, metadata segura y errores.
- `core/services/report_history.py`: servicio compartido para iniciar, cerrar y listar registros de histórico, con backend en memoria para pruebas.
- `web/app/main.py`: instrumentación de `POST /api/reports/sla` y `POST /api/flows/repetitividad`; `GET /api/reports/history` ahora consulta PostgreSQL y conserva `files` como compatibilidad básica.
- `web/frontend/src/views/ReportsHistoryView.vue`: vista convertida en tabla filtrable por tipo, estado y período, con salidas descargables y errores visibles.

- Documentación del histórico agregada en `docs/db.md`, `docs/api.md`, `docs/web.md`, `docs/informes/sla.md` y `docs/informes/repetitividad.md`.

## Riesgos y Pendientes

- La suite focal de API no pudo ejecutarse en la venv local porque falta `asyncpg`; las pruebas quedaron agregadas para correr en Docker/CI con dependencias completas.
- El rate limit de login es in-memory y adecuado para dev; producción multiworker o multiinstancia debe migrarlo a Redis u otro backend compartido.
- Los hashes bcrypt legacy siguen verificando para no invalidar usuarios existentes; la migración total requiere rehash gradual al cambiar contraseña o en un futuro login exitoso.
- En dev existente, ejecutar `./scripts/setup_local_secrets.sh` o `./Start` para crear `.secrets/api_key_v1.txt` antes de reconstruir/levantar la API.
- `npm run build` en `web/frontend` no pudo ejecutarse localmente porque `vite` no está instalado en `node_modules`.
- `tests/test_web_sla_flow.py tests/test_web_repetitividad_flow.py` quedaron no concluyentes en la venv local: `TestClient(app)` se bloqueó antes de llegar a las rutas, incluso con `/health`.
- `alembic upgrade head --sql` no pudo generar SQL offline por una migración antigua (`20251013_01_add_geo_to_cases.py`) que inspecciona DB en modo offline.
- `alembic upgrade head` no pudo aplicarse desde la venv local: la URL default apunta a `postgres` fuera de la red Docker y el intento contra `127.0.0.1:5433` no logró conexión con Postgres dev.
