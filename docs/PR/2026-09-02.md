# PR Diario - 2026-09-02

## Resumen de Cambios

Integración con la API interna PROV (`API_Contexto_Servicio`) para enriquecer `Servicio` con datos
de última milla (nodo/equipo/puerto) y el historial completo de upgrades de ID (fecha, estado,
motivo por eslabón), sin retirar el flujo de ingesta Excel existente (`POST /servicios/ingest`).
Ejecutado vía `superpowers:subagent-driven-development`, 12 tareas (originalmente 11; se insertó una
Task 11 a mitad de ejecución tras un gap real encontrado en la revisión de la Task 10 — ver más
abajo). Diseño en `docs/superpowers/specs/2026-09-02-servicios-prov-integracion-design.md`, plan en
`docs/superpowers/plans/2026-09-02-servicios-prov-integracion.md`. Detalle completo de decisiones en
`docs/decisiones.md`, entrada "2026-09-02 (cont.) — Integración con la API PROV".

### Backend: paquete `core/services/prov/`

Cliente HTTP async nuevo, mismo patrón que `core/services/cromo/`:

- `config.py`: `ProvConfig` (dataclass) + `get_settings()` cacheado; lee `PROV_BASE_URL` y los
  secrets `api_prov_user_v1`/`api_prov_pass_v1` vía `get_secret()`, valida al construirse (no en
  import time).
- `rate_limiter.py`: `AsyncTokenBucketLimiter` — pacing uniforme, protegido con `asyncio.Lock`,
  fuerza el máximo de 5 req/s (`PROV_RATE_LIMIT_PER_SECOND`) tanto para el endpoint on-demand como
  para el backfill masivo.
- `client.py`: `ProvClient` (`httpx.AsyncClient` + `httpx.BasicAuth` por-request, reintentos con
  backoff exponencial en errores de red/5xx). `obtener_contexto_servicio(nro_servicio)` distingue
  éxito de error lógico por el **tipo** de `Resultado:` en el payload (objeto → éxito; string → sin
  contexto) y traduce ese caso a `ProvServicioNoEncontradoError` — nunca una excepción sin manejar.
- `ingesta.py`: `ingerir_contexto_prov(session, servicio, contexto_raw)` reusa **sin modificar**
  `consolidar_identidad_servicio`/`resolver_estado_servicio`/`es_verificable_por_tipo_y_estado` de
  `core/services/servicios_consolidacion_service.py`. Traduce `estado_comercial`
  (`INSTALADO`/`DADO BAJA`) a `Activo`/`Baja`, actualiza cliente/dirección/tipo, y reescribe completas
  (delete + reinsert) las filas de `ServicioEquipoUltimaMilla` y `ServicioHistorialId` — PROV siempre
  devuelve el estado vigente completo, nunca un delta.

### Endpoints (`api/app/routes/servicios.py`)

- `POST /servicios/prov/refrescar?id=...`: mismo criterio de búsqueda que `/detail`. Llama a
  `ProvClient.obtener_contexto_servicio`, corre `ingerir_contexto_prov`, hace commit y devuelve el
  detalle actualizado. 404 si el `Servicio` no existe en la DB o si PROV no tiene contexto para ese
  número (`ProvServicioNoEncontradoError`).
- `GET /servicios/detail` (existente): extendido con `historial_ids`/`equipos_ultima_milla`, leyendo
  siempre de la DB (nunca llama a PROV) — decisión explícita para no acoplar la vista de detalle al
  rate-limit del cliente.
- `POST /servicios/ingest` (Excel): sin cambios.

### Proxy web + fix de CSRF (Task 11, gap real encontrado durante la ejecución)

La revisión de la Task 10 confirmó con curl real contra `lasfocasdev-web` que el botón nuevo
"Actualizar desde PROV" no funcionaba en un navegador real: `web/app/main.py` expone su propio
FastAPI que proxya **a mano, ruta por ruta**, cada endpoint de `/api/servicios/*` (no hay un proxy
genérico `/api/{path:path}`), y el `POST /servicios/prov/refrescar` del backend nunca tuvo su
contraparte proxy. Se agregó `servicio_prov_refrescar_web` en `web/app/main.py` (mismo patrón que
`servicio_verificable_web`). Al diseñar el proxy se encontró un segundo bug real en la misma cadena:
`refrescarServicioDesdeProv` (`web/frontend/src/api/servicios.ts`) pasaba `csrf: true` sin un
`json`, y `request()` (`client.ts`) sólo inyecta `csrf_token` cuando `json` es un objeto truthy — el
POST salía sin body. Fix: agregar `json: {}`. Ambos cerrados en el commit `7147b61`, verificado con
curl real post-rebuild (401 "No autenticado" sin cookie de sesión, no 404/405 — confirma que la ruta
quedó cableada).

### Backfill masivo (`scripts/servicios_backfill_prov.py`)

Mismo patrón que `scripts/servicios_backfill_no_verificable_por_baja.py` (`--apply`, dry-run por
default), pero async de punta a punta (`AsyncSessionLocal`) porque `ProvClient` lo es. Reusa
`ingerir_contexto_prov` — la misma función que usa el endpoint on-demand. Candidatos: todas las
filas de `app.servicios` con `numero_primer_servicio IS NOT NULL`, ordenadas por `id`; acepta
`--solo-ids ID1,ID2,...` para un subconjunto acotado. Respeta el rate limiter durante todo el
recorrido. Verificado real contra dev con `--solo-ids` (1 fila en cada tabla nueva para
`numero_primer_servicio=122214`, confirmado con `psql` antes/después).

## Impacto y Riesgos

- **Rate limit combinado backfill + uso interactivo**: el cliente PROV nunca supera 5 req/s dentro de
  un mismo proceso (`AsyncTokenBucketLimiter`), pero la API (`uvicorn` sin `--workers`) y el script de
  backfill corren en procesos separados, cada uno con su propio limiter — no hay limiter distribuido
  (Redis), decisión explícita por sobre-ingeniería para el volumen esperado. Si el backfill masivo
  corriera junto con uso interactivo intensivo del botón "Actualizar desde PROV", el máximo combinado
  teórico sube a ~10 req/s. Riesgo aceptado y documentado (`docs/decisiones.md`); recomendación
  operativa: no correr el backfill masivo en horario de uso intensivo.
- **Backfill sin catch-all por fila**: `scripts/servicios_backfill_prov.py` captura
  `ProvServicioNoEncontradoError`/`ProvClientError` por fila (no encontrado / error de transporte),
  pero no envuelve `ingerir_contexto_prov`/`session.commit()` en un `try/except` genérico — una fila
  con datos anómalos que rompa el parseo o viole una constraint de DB aborta todo el recorrido sin
  loguear el resumen final. Aceptable para corridas acotadas (`--solo-ids`); revisar antes de una
  corrida `--apply` sobre toda la tabla `servicios`.
- **Producción sin secrets/compose para PROV**: sólo dev tiene los archivos de secrets y el bloque
  `secrets:` de `docker-compose.dev.yml`. No hay ventana de despliegue en el alcance de esta
  integración — pendiente documentado, no implementado.
- **Traducción `estado_comercial` → `estado_servicio`** cubre sólo los dos valores observados en los
  payloads reales consultados (`INSTALADO`, `DADO BAJA`); valores nuevos de PROV requieren ampliar el
  diccionario en `core/services/prov/ingesta.py` cuando aparezcan.
- **Gap real cerrado en la propia ejecución (Task 11)**: el plan original (Tasks 1-10) no contempló
  `web/app/main.py` como una capa de proxy manual — cualquier endpoint nuevo bajo
  `api/app/routes/servicios.py` necesita su proxy explícito ahí para ser alcanzable desde el
  frontend; no es automático. Ver `docs/decisiones.md` para el detalle completo.
- **Frontend sin test runner**: no hay `vitest` en el proyecto — los cambios de Vue (`ServiceTimeline.vue`,
  integración en `ServicioDetalleView.vue`) se verificaron por build + revisión de código + curl real
  contra el proxy, sin captura de pantalla en navegador durante esta sesión.
