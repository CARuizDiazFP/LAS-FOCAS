### Errores y bloqueos

1. **Bug real de idempotencia en el backfill de Cromo** (detectado en `--dry-run` de esta misma
   sesión, nunca tocó datos reales): la clasificación "¿esta Cámara raíz ya es un padre?" —tanto en
   `resolver_o_crear_padre_desde_base` (función compartida, usada también por el listener de Slack)
   como en la resolución en memoria propia del script— sólo miraba `Camara.botellas` (self-FK
   legado). Una Cámara padre creada por el backfill de Cromo tiene cero Botellas legado (sus hijas
   son `CromoBotella`, tabla distinta vía `camara_id`), así que en cualquier corrida posterior se la
   trataba como "pelada" y se la absorbía como Botella de un padre nuevo duplicado, rompiendo el
   invariante "`camara_id` siempre apunta a una raíz". El `--dry-run` detectó ~400 vinculaciones que
   habrían quedado inválidas.
2. **Confusión real de contenedores durante la verificación**: `docker exec lasfocasdev-api curl
   .../api/infra/botellas/buscar` devolvió 404 con `{"detail":"Not Found"}` y `GET /openapi.json`
   con `paths` vacío. Se asumió que `lasfocasdev-api` servía `web/app/main.py` (el backend real de
   la SPA); en realidad corre `api/app/main.py` — una app FastAPI totalmente distinta ("LAS-FOCAS
   API", auth por API key). Ambos contenedores corren `uvicorn app.main:app` desde el mismo path
   interno `/app/app/main.py`, pero cada imagen copia ahí un archivo fuente distinto.
3. **2 archivos de test rotos por el fix de idempotencia**: `tests/test_cromo_camara_padre_service.py`
   y `tests/test_camara_hierarchy_service.py` usaban `session.query.return_value.filter.return_value
   .all.return_value = [...]` para una sola consulta mockeada. El nuevo helper
   `ids_camaras_con_cromo_hijos` agrega una segunda consulta contra el mismo chain compartido del
   mock, y la lista mockeada (pensada para la primera consulta) se intentaba desempaquetar como
   tuplas `(camara_id,)` — `TypeError: cannot unpack non-iterable Camara object`.
4. **Bug real de propagación de estado** (reportado por el usuario desde el dashboard: Botellas
   mostrando `OCUPADA` sin ningún ingreso real): verificado contra `lasfocasdev-postgres`, **0**
   `Ingreso` activos en todo el sistema, pero **295** `CromoBotella` con `estado` (`OCUPADA`/
   `BANEADA`) que ya no coincidía con el de su propia Cámara padre (`LIBRE`). `aplicar_estado_a_grupo`
   —el único punto de escritura sancionado de `Camara.estado`— nunca tocaba `CromoBotella.estado`.
5. **`docker cp` falló al reconstruir para el segundo fix**: `docker cp scripts/archivo.py
   lasfocasdev-api:/app/scripts/archivo.py` devolvió "Could not find the file /app/scripts". El
   directorio `scripts/` nunca formó parte de la imagen Docker de `api`/`web` — había sido copiado
   ad-hoc como directorio completo en una parte anterior de la sesión (ya compactada) y se perdió al
   recrear el contenedor desde la imagen reconstruida.
6. **Log mal etiquetado** encontrado al releer `cromo_backfill_camara_padre.py` antes de re-correrlo:
   la condición `if estado_mapeado != CamaraEstado.NO_OPERATIVA` disparaba un `logger.warning` con el
   texto `hallazgo=hereda_estado_no_operativa` — exactamente lo opuesto de lo que describía la
   condición real (el hallazgo genuino era "hereda un estado que NO es no_operativa"). No afectaba el
   valor escrito en `botella.estado` (correcto en ambos casos), sólo el texto del log de auditoría.

### Soluciones aplicadas

1. → `core/services/camara_hierarchy_service.py::ids_camaras_con_cromo_hijos` (función nueva: set de
   IDs de `Camara` con al menos una `CromoBotella` propia, una sola consulta) reusada en
   `resolver_o_crear_padre_desde_base` (chequeo de "ya establecido" + absorción de "peladas") y en
   `scripts/cromo_backfill_camara_padre.py` (clasificación en memoria de Fase 1). Verificado con
   `--dry-run` tras el fix: 0 violaciones del invariante (antes ~400). Backfill real corrido después:
   0 violaciones post-commit.
2. → Identificado comparando `docker inspect --format '{{.Config.Cmd}}'` de ambos contenedores y
   leyendo directamente `/app/app/main.py` en cada uno (`api/app/main.py` vs `web/app/main.py`,
   mismo path interno, código fuente distinto). Documentado como memoria persistente
   (`feedback_container_api_vs_web_main.md`) para no repetir la confusión en sesiones futuras.
3. → `pytest.fixture(autouse=True)` en ambos archivos de test que hace `monkeypatch.setattr(
   "core.services.camara_hierarchy_service.ids_camaras_con_cromo_hijos", lambda session: set())`
   por defecto; los tests que sí quieren ejercitar la protección real sobreescriben ese mismo patch
   dentro del test. Los 9 tests existentes siguieron pasando sin tocar su lógica interna.
4. → `core/services/camara_estado_service.py::aplicar_estado_a_grupo` extendido: además de escribir
   `Camara.estado`, ahora sincroniza en la misma transacción las `CromoBotella` vinculadas a
   cualquier miembro del grupo efectivamente modificado, vía `MAPEO_ESTADO_CROMO` (movido a este
   módulo desde `scripts/cromo_backfill_camara_padre.py`, que ahora lo importa en vez de mantener su
   propia copia). Corrección retroactiva: `scripts/resync_cromo_botella_estado.py` (nuevo,
   `--dry-run` soportado) — corrida real: 295 filas corregidas, 0 desincronizadas verificado
   post-commit. Verificado en vivo (con rollback, sin mutar datos reales) que banear una Cámara
   padre con Botellas Cromo propias sincroniza ambas tablas en la misma operación.
5. → `docker cp scripts lasfocasdev-api:/app/scripts` (directorio completo, no archivo por archivo)
   para restaurar el directorio faltante antes de poder correr cualquier script de nuevo.
6. → Invertida la condición y corregido el texto (`hallazgo=hereda_estado_restrictivo_real`), sin
   cambiar ningún comportamiento real — sólo la claridad del log de auditoría.

### Mejoras de arquitectura agéntica propuestas

- **`docker-rebuild` (skill existente, `.github/skills/`)** — agregar dos guardrails reales
  encontrados esta sesión: (a) `lasfocasdev-api` y `lasfocasdev-web` corren el mismo comando desde
  el mismo path interno pero código fuente distinto (`api/app/main.py` vs `web/app/main.py`) — un
  curl que da 404 con `{"detail":"Not Found"}` en vez de 401/403 debe hacer sospechar primero del
  contenedor equivocado; (b) el directorio `scripts/` no está incluido en ninguna de las dos
  imágenes Docker — tras cualquier rebuild/recreate, cualquier script que se necesite correr por
  `docker exec` requiere `docker cp scripts lasfocasdev-api:/app/scripts` de nuevo. Esto habría
  evitado los dos bloqueos reales #2 y #5 de esta sesión sin necesidad de investigar desde cero.
- **`pytest-focas` (skill existente, `.github/skills/`)** — agregar el patrón real encontrado: al
  extender una función ya testeada con `session = MagicMock()` y un chain plano
  (`session.query.return_value.filter.return_value.all.return_value = [...]`) para que haga una
  consulta ADICIONAL contra el mismo modelo u otro, los tests existentes rompen con errores confusos
  (`TypeError: cannot unpack...`) porque ambas consultas comparten el mismo mock. Recomendar el
  patrón de `pytest.fixture(autouse=True)` + `monkeypatch.setattr` sobre la función/helper interno
  que hace la consulta nueva, en vez de intentar que el mismo `session.query` mockeado sirva para
  ambas. Habría evitado la investigación puntual del error #3.
