### Errores, bloqueos y soluciones aplicadas

1. **Verificación E2E real dio 500 que parecía un bug nuevo — era código stale del contenedor.**
   - **Síntoma:** `curl` real contra `POST /servicios/ingest` en `lasfocasdev-api` con el Excel real
     dio `IntegrityError: duplicate key ... servicio_id=89869`, aparentando un bug no cubierto por
     ninguno de los tests/revisiones previas.
   - **Causa raíz confirmada:** `docker inspect lasfocasdev-api --format '{{.Created}}'` mostraba la
     imagen construida a las 12:35 UTC — ~4 horas antes de que se aplicara cualquiera de los fixes
     del día (`git log --date=iso-strict` de los commits de fix, 16:04-17:01 UTC). Los tests de los
     implementadores (`TestClient(app)` in-process contra el código del host) nunca podían detectarlo
     — sólo ejercitan el checkout, nunca la imagen realmente deployada.
   - **Solución:** `docker compose -f deploy/docker-compose.dev.yml --env-file .env.dev build api web
     && up -d api web`. Reintentado el mismo curl: 200 OK, comportamiento correcto confirmado
     (incluido exactamente el caso `numero_primer_servicio=7700` que había reventado).
   - **Condición de regresión futura:** cualquier verificación E2E real de cierre de un ciclo
     `subagent-driven-development` que toque un contenedor debe reconstruirlo primero — no asumir
     que está al día porque los tests (in-process) pasaron. Ver memoria
     `feedback_sdd_verificar_imagen_contenedor_antes_de_e2e.md`.

2. **Un implementador (Opus) falló a mitad de tarea por un error transitorio de API (límite de
   sesión), dejando trabajo parcial válido sin commitear.**
   - **Síntoma:** el dispatch de la Tarea de fusión de placeholders (Fix C1) terminó con
     `status: failed` / "Agent terminated early due to an API error: session limit" a mitad del ciclo
     TDD (fixture de test ya escrita, tests todavía no).
   - **Causa raíz:** límite de sesión de la API del subagente, no un problema de diseño/código —
     confirmado revisando `git diff` del archivo de test tocado: el contenido dejado era coherente y
     había descubierto un hecho real (`cromo_servicio_match.servicio_id` sin `ON DELETE CASCADE`) que
     validaba el diseño del fix.
   - **Solución:** redespachar un implementador fresco (mismo modelo) con instrucción explícita de
     retomar el diff parcial en vez de rehacerlo desde cero, citando el hecho ya descubierto para que
     no se perdiera la investigación real.
   - **Condición de regresión futura:** ante un `status: failed` de un implementador (no
     `BLOCKED`/`DONE_WITH_CONCERNS`), revisar primero `git diff` de los archivos tocados antes de
     redespachar — puede haber trabajo real y válido que rehacer desde cero desperdiciaría.

3. **El propio diseño del plan (no del implementador) tenía 2 bugs reales en el código que le di al
   implementador de la Tarea 4, descubiertos por el revisor con trazado manual explícito pedido.**
   - **Síntoma:** el código de `consolidar_identidad_servicio` que yo mismo escribí en el brief tenía
     una colisión `None == None` (dos valores no numéricos distintos tratados como iguales) y un
     `max()` no determinístico sobre un `set` con hash randomizado por proceso.
   - **Causa raíz:** al diseñar la función pensando en los 5 casos de test que yo mismo especifiqué,
     no consideré variantes (empates numéricos, valores no numéricos distintos) — el revisor sí, tras
     pedirle explícitamente "pensá en un caso no cubierto por los tests existentes y verificalo a
     mano".
   - **Solución:** 2 rondas de fix (filtrado simétrico de alias, canonicalización temprana de cada ID
     al entrar a la función) + fuzz-testing de 363k casos para cerrar la clase completa de bug, no
     sólo el caso puntual reportado.
   - **Condición de regresión futura:** cuando el código de un brief lo escribo yo (no una
     transcripción neutral), pedirle EXPLÍCITAMENTE al revisor que no confíe en que "el controlador
     ya lo pensó" — el propio diseño puede tener el mismo tipo de bug que cualquier implementación.
