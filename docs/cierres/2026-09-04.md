### Tarea planteada

El usuario reportó (rol asignado: "Ingeniero de Software Backend / Web Scraping / Integración de
APIs") un supuesto bug en `core/services/prov/` (o `core/parsers/`): para servicios PROV en estado
"BAJA" (ejemplos dados: 41146, 100560), la sincronización no persistía Cliente ni Domicilio, mientras
que en "ALTA" (119732) sí funcionaba. Hipótesis del ticket: un "early return"/excepción en el parser
al no encontrar el bloque de "Contexto" ("Contexto no creado" en la UI de PROV) bloqueaba también la
extracción de Cliente/Domicilio, pese a que esos datos aparecen en una "tabla superior de metadatos"
separada en la UI de PROV.

### Investigación realizada y hallazgos

1. **Localización real del módulo** (2 agentes Explore en paralelo): `core/services/prov/` existe
   (`client.py`, `config.py`, `ingesta.py`, `rate_limiter.py`), pero **no es web scraping de HTML** —
   es un cliente REST JSON contra `API_Contexto_Servicio` de PROV
   (`https://prov.metrotel.com.ar/api/v1/ADMEQ/API_Contexto_Servicio`). `core/parsers/` no tiene
   relación (sólo parsers de Excel/tracking). El string literal "Contexto no creado" **no existe en
   ningún lugar del repo**. Documentado ya en `docs/superpowers/specs/2026-09-02-servicios-prov-integracion-design.md`,
   `docs/decisiones.md` y `docs/db.md` desde la integración original (2026-09-02).
2. **Verificación contra el código real**: `parsear_contexto_prov`/`ingerir_contexto_prov`
   (`core/services/prov/ingesta.py`) usan guards (`if parseado.nombre_cliente:`, `if
   parseado.equipos:`) que ya evitan pisar datos existentes con `None`, y
   `consolidar_identidad_servicio` ya descarta valores vacíos (`_es_valor_util`) sin corromper la
   identidad del servicio. `ProvServicioNoEncontradoError` (la única excepción real del cliente) sólo
   se dispara cuando `Resultado:` es un string (servicio inexistente en PROV) — no tiene relación con
   estados ALTA/BAJA.
3. **Verificación contra el sistema real** (crítico — la premisa del ticket no se dio por válida sin
   probarla): se consultó `ProvClient` real, con las credenciales ya configuradas en
   `.secrets/Dev_api_prov_*`, contra los 3 números de servicio exactos del ticket, desde
   `lasfocasdev-api`:
   - **119732 (INSTALADO)**: `Resultado:` completo (`Descripcion`, `Direccion1`, `Provincia1`,
     `Nodo1`, `Equipo1`, `Port1`, etc.) — como se esperaba.
   - **41146 y 100560 (DADO BAJA)**: `Resultado:` **es un objeto exitoso** (no dispara ninguna
     excepción) pero PROV lo devuelve truncado a
     `{"subproducto": ..., "nro_servicio_original": ..., "estado_comercial": "DADO BAJA"}` — sin
     `Descripcion` ni `Direccion{N}`/`Provincia{N}` en absoluto.
   - **Conclusión verificada**: la premisa del ticket (early-return/excepción de nuestro código) es
     **incorrecta**. El código de LAS-FOCAS no bloquea ni pierde datos disponibles; el gap es que
     **PROV mismo no incluye Cliente/Domicilio en este endpoint para servicios de baja**.
4. **Descarte de endpoint alternativo**: se buscó en todo el repo cualquier otra referencia `API_*`
   de PROV (sin resultados) y se probó `GET .../API_ADMEQ/help` contra el sistema real para ver si
   la cuenta tenía visibilidad de otras acciones — devolvió `401: "api-claude no esta autorizado a
   utilizar la accion ADMEQ:help"`. Esto confirma que PROV autoriza por acción de forma granular y
   que la cuenta `api-claude` está limitada a `Contexto_Servicio`. Se decidió **no** seguir probando
   nombres de acción a ciegas contra el sistema de producción de Metrotel (enumeración no autorizada).
